# Windows Programming Course Template

Use this reference for C++/Windows/MFC/Win32/GDI programming courses.

## Course Boundary Defaults

Prefer:

- Win32 API, MFC, GDI, standard C++.
- Visual Studio, MinGW, or the toolchain already used by the student.
- Resource files, menus, dialogs, controls, message handlers, document-view structures.

Avoid unless explicitly allowed:

- Qt, wxWidgets, ImGui, Direct2D, DirectX, OpenGL, Electron, web UI frameworks.
- Complex build systems if the class has not introduced them.
- Advanced C++ metaprogramming, heavy template abstractions, or unnecessary design patterns.

## Common Lecture-To-Code Mappings

| Lecture concept | Code/API | Program behavior | Student explanation |
|---|---|---|---|
| WinMain | `WinMain`, `RegisterClass`, `CreateWindow`, message loop | Program starts and owns a window | "This is the GUI program entry and event loop." |
| Window procedure | `WndProc` | All window messages are dispatched here | "Windows sends messages; we switch by message type." |
| Command messages | `WM_COMMAND` | Menus/buttons trigger actions | "User commands are identified by control/menu IDs." |
| Paint messages | `WM_PAINT`, `BeginPaint`, `EndPaint` | Window redraws itself | "Drawing belongs in paint handling so it can be restored." |
| Device context | `HDC`, `CDC` | Target for drawing operations | "GDI drawing happens through a DC." |
| Pen | `CreatePen`, `CPen` | Controls line style, width, color | "The pen is selected into the DC before drawing lines." |
| Brush | `CreateSolidBrush`, `CreateHatchBrush`, `CBrush` | Controls fill color/pattern | "The brush fills closed shapes." |
| Mouse interaction | `WM_LBUTTONDOWN`, `WM_MOUSEMOVE`, `WM_LBUTTONUP` | Drag-to-draw behavior | "Press starts, move previews, release commits." |
| Document-view | document data + render function | Data is separated from display | "The view redraws from document data." |
| Serialization | `Serialize`, `Save`, `Load`, file streams | Save/open document data | "Editable data is stored, not just a screenshot." |

## Suggested Lab Pattern

For each lab, use this minimum structure:

```text
1. Reference concept from PPT.
2. Minimal visible feature.
3. Data model.
4. Message flow.
5. Drawing/output function.
6. Save/load or verification if relevant.
7. Explanation artifacts.
```

## Standard Prompt For Live Class

```text
We are in a Windows C++ programming class.
The teacher just explained: [concept].
Use only [Win32/MFC/GDI/standard C++] and avoid [forbidden frameworks].
Explain the concept in simple terms, then map it to:
1. the Windows message/API involved,
2. a minimal code skeleton,
3. a possible bug students should watch for,
4. one classroom question the teacher can ask.
```

## Standard Prompt For Lab Project

```text
Use the attached PPT and teacher notes to design a small Windows C++ lab.
Requirements:
- use only course-level APIs: [allowed APIs]
- avoid: [forbidden APIs]
- include a concept-to-code table
- produce runnable code
- add Chinese comments around lecture-linked code
- write README build/run/demo instructions
- generate a student explanation script and likely teacher Q&A
Before coding, summarize the implementation boundary and ask if it matches the course level.
```

## Student Defense Questions

Use these after implementation:

1. Which lecture concept is demonstrated by this function?
2. What message triggers this code?
3. What data is stored, and where?
4. Why is drawing done in `WM_PAINT` or `OnDraw`?
5. Which parts were generated by AI, and which parts did you modify?
6. How did you verify the program?
7. What would break if this code were removed?
8. What did the reference/demo not have that your version added?
