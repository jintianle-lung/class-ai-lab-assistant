# CLASS-AI：课堂 AI 辅助实验框架

## 定位

CLASS-AI 是一个面向程序设计课的课堂与课后闭环框架。它的目标不是让 AI 替学生完成作业，而是让 AI 成为“可被教师控制、可被学生质疑、可被代码验证”的课堂助教。

适用场景：

- 老师课上讲完 PPT、示例代码或实验要求后，希望现场调用 AI 生成解释、伪代码、流程图或对比案例。
- 学生课后把 PPT、老师口述内容和实验要求交给 AI，让 AI 辅助实现一个课程范围内的项目。
- 项目完成后，AI 反过来帮助学生生成架构图、关键代码讲解、验收讲稿和老师问答。

## 框架来源

本框架综合参考了以下成熟方向：

- UNESCO 生成式 AI 教育指导：强调人本、伦理、安全和教学设计。
- UNESCO 教师 AI 能力框架：强调教师主导、AI 教学法、伦理和专业成长。
- Stanford AI Literacy：强调 functional、ethical、rhetorical、pedagogical 四类 AI 素养。
- TeachAI：强调 AI literacy 的课堂可落地资源与示例。
- AI Assessment Scale：强调在作业中明确 AI 允许使用到什么程度。
- LAIR：强调 Literacy、Application、Interpretation、Responsibility。
- EQAITE：强调教学价值、教师自主性、评价有效性、学生能动性。
- Andrej Karpathy 的公开教学方式：强调从零搭建、最小可运行系统、代码优先、逐步迭代和实证验证。

## Karpathy-style 改进原则

这部分是对 CLASS-AI 的工程化补强。它解决一个常见问题：AI 很容易一上来生成完整大项目，学生看起来拿到了结果，但不一定真的理解。

所以每个实验都要按下面的顺序长出来：

```text
最小可运行基线 -> 一步一个改进 -> 每步都能运行 -> 图解对应代码 -> 学生能讲回来
```

### 1. 先做最小可运行版本

不要一开始就让 AI 生成完整项目。先做最小版本。

例如画图程序：

```text
版本 0：创建窗口，能响应 WM_PAINT
版本 1：用 GDI 画一条固定直线
版本 2：用鼠标拖动来画线
版本 3：把每一笔保存成 Stroke 数据
版本 4：WM_PAINT 根据 Stroke 列表重绘
版本 5：增加保存、导出和工具条
```

这样学生能看见程序是怎么一步步长出来的。

### 2. 让核心循环暴露出来

每个程序都要讲清楚主循环。

Windows 程序的核心循环是：

```text
用户操作 -> Windows 消息 -> WndProc -> 数据变化 -> WM_PAINT -> GDI 绘制 -> 屏幕显示
```

AI 生成的图、代码和讲稿都必须围绕这个循环，不要只堆功能。

### 3. 图解必须锚定代码

架构图不能只是漂亮。每个模块旁边都应该能写出对应代码：

```text
消息处理层 -> WndProc
绘图层 -> PaintWindow / RenderDocument / DrawStroke
数据层 -> DrawingDocument / Stroke
保存层 -> Save / Load / ExportCanvasBitmap
```

学生讲图时必须能马上跳到对应函数。

### 4. 每一步都要能验证

不是“看起来应该可以”，而是要运行。

例如：

```text
能打开窗口
能画图
遮挡窗口后图形不丢
能保存 .psp
能导出 .bmp
能重新构建通过
```

### 5. AI 是放大器，不是答案机

AI 可以帮助：

- 解释概念
- 生成最小代码
- 找 bug
- 画架构图
- 写讲稿

但学生必须负责：

- 运行代码
- 修改代码
- 判断是否超纲
- 解释代码和课堂知识的对应关系
- 说明 AI 哪里可能错

## CLASS-AI 六步

### C - Capture：课堂捕获

收集课堂输入：

- PPT
- 老师口述重点
- 板书
- 示例代码
- 学生提问
- 实验要求

AI 输出：

- 本节课核心知识点
- 老师强调内容
- 适合落地成项目的功能
- 不应超纲的技术边界

### L - Link：知识映射

把课堂概念映射到代码。

示例：

| 课上知识点 | 代码/API | 程序表现 | 验收讲法 |
|---|---|---|---|
| 消息循环 | `GetMessage` / `DispatchMessage` | 程序持续响应用户操作 | Windows 程序由消息驱动 |
| 窗口过程 | `WndProc` | 集中处理鼠标、菜单、绘制消息 | 每个消息对应一种行为 |
| GDI 绘图 | `HDC` / `HPEN` / `HBRUSH` | 画线、矩形、椭圆 | 绘图必须通过设备环境 |
| 正确重绘 | `WM_PAINT` | 遮挡、缩放后恢复图形 | 图形不能只画一次，要能重画 |
| 文档-视图 | 数据类 + 绘制函数 | 数据和显示分离 | 文档维护数据，视图负责显示 |

### A - Ask in Class：课上调用 AI

老师现场调用 AI，但要让学生参与判断。

推荐节奏：

1. 老师讲完一个概念。
2. AI 用简单语言解释概念。
3. AI 生成最小代码或流程图。
4. 学生找 AI 输出的问题。
5. 老师修正并总结。

示例提示词：

```text
我们正在上 Windows 程序设计课，刚讲完 WM_PAINT。
请用不超出 Win32/GDI 的方式解释它，并说明为什么绘图程序不能只用鼠标消息里直接画图。
输出：概念解释、最小代码骨架、一个常见错误、一个课堂提问。
```

### S - Scaffold：实验搭建

AI 根据课堂材料搭建最小可运行项目。

要求：

- 先输出最小可运行基线，再逐步加功能。
- 只使用本节课或前面课程讲过的技术。
- 代码能编译运行。
- 注释标明对应课堂知识点。
- README 写清楚构建、运行、演示方式。
- 学生必须修改或补充一部分，而不是原样提交。

### S - Show：可视化讲解

AI 生成：

- 架构图
- 消息流程图
- 数据流图
- 关键代码精讲
- 演示步骤
- 老师可能问的问题

目标是让学生快速讲清楚：

```text
课堂知识点 -> 代码实现 -> 程序行为 -> 验证证据
```

每张图都要标出对应代码函数名，避免变成空泛流程图。

### AI - Assess & Iterate：评估与迭代

每次实验结束后要求学生回答：

1. AI 帮我做了什么？
2. 哪些地方我修改过？
3. 哪些代码对应老师课上讲的知识？
4. 我如何证明程序能运行？
5. 如果不用 AI，我还需要补哪些基础？

## AI 使用等级

| 等级 | 名称 | 允许范围 | 适合场景 |
|---|---|---|---|
| Level 0 | 不使用 AI | 学生独立完成 | 基础语法、闭卷测验 |
| Level 1 | AI 解释 | 只解释概念，不写代码 | 新概念引入 |
| Level 2 | AI 规划 | 流程图、伪代码、思路 | 课上讨论 |
| Level 3 | AI 协作 | 生成部分代码，学生修改 | 普通实验 |
| Level 4 | AI 构建 + 学生答辩 | 生成完整项目，但必须修改、验证、讲解 | 综合作业 |
| Level 5 | AI 探索 | 师生共同设计新工具或新流程 | 教改探索 |

## 一次课的推荐流程

```text
课前：老师准备 PPT、示例代码、AI 使用等级
课中：老师讲概念 -> AI 生成最小例子 -> 学生质疑 -> 老师修正
课后：学生提交 PPT/笔记/要求给 AI -> AI 先做基线 -> 再逐步加功能
验收：学生运行程序 -> 讲架构图 -> 跳到关键代码 -> 回答老师问题
复盘：学生说明 AI 帮助、人工修改、验证证据
```

## 一个标准实验包应该包含

```text
1. 本节课知识点整理
2. 概念到代码映射表
3. 最小可运行基线
4. 逐步改进清单
5. 最终代码
6. 架构图和流程图
7. 关键代码精讲
8. 构建/运行/验证记录
9. 学生验收讲稿
10. 老师可能提问与回答
```

## 关键原则

- 老师控制目标和边界。
- AI 输出必须被学生质疑和验证。
- 代码必须能运行。
- 图解必须能对应代码。
- 最终评价学生是否理解，而不是评价 AI 是否会写代码。
